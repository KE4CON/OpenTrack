# OpenTrack Fine-Tooth-Comb Audit — 2026-08-10

**Why this audit exists:** the OpenTrack code to date was written in a chat session and applied via zip
handoffs — it was never built, run, or tested in a verification loop. This audit combs it in Claude Code
(direct build/test/trace) using the multi-lens standard from `AUDIT_METHODS.md`: security/authorization
(M6, top priority for a self-hosted web app), data-layer/EF correctness + web↔desktop parity, and
reachability/orphaned features (M7 — the "built but not wired" class).

Baseline: solution builds clean (0 warnings / 0 errors). Test projects contain **only the default
`UnitTest1.cs` template — zero real tests.** Every finding below was traced to specific code and, where two
reviewers disagreed, reconciled against the source.

---

## Systemic root cause (drives most Critical/High findings)

`ProjectMembership` (with a per-project `Role`), `Issue.IsPrivate`, and `Project.IsPublic` all exist, are
persisted, and are editable in the UI — **but not one of them is ever read for an authorization decision
anywhere in the codebase.** The only thing ever consulted is the caller's single **global** `User.Role`
claim (`OpenTrack.Role`). Per-project scoping and privacy are therefore decorative, on **both** the API path
and the web/EF path (no safe fallback). The role check itself fails *closed* (good), but it only ever asks
the global question.

---

## Findings (deduplicated, severity-ranked)

### CRITICAL

- **C1 — Private issues are not private.** `Issue.IsPrivate` is written and returned but never filtered on
  any read path: API `GET /api/issues` and `GET /api/issues/{id}`
  (`IssueEndpoints.cs:29`, `:42`) and web `DbOpenTrackDataService.GetIssuesAsync`/`GetIssueAsync`. Any
  authenticated user can enumerate and read every "private" issue in every project. Private notes
  (`IssueNote.IsPrivate`) are likewise returned to everyone (and the note DTO doesn't even carry the flag,
  so the UI couldn't filter them if it wanted to).
- **C2 — Full IDOR on projects and issues (read + write).** `GET /api/projects`, `/{id}`,
  `/{id}/categories`, `/{id}/members` return any project regardless of `IsPublic`/membership (leaking member
  usernames). Writes are gated only by a **global** role tier, never by ownership/membership: a global
  "Updater" can edit/close/reassign any issue in any project; a global "Manager" can rename any project or
  flip it public (`IssueEndpoints.cs:93`, `ProjectEndpoints.cs:61`). The web/EF path has no authz in the
  data service at all — it relies solely on the page `[Authorize(Policy=…)]`, which is again the global tier.

### HIGH

- **H1 — Blazor Server shares one `AppDbContext` per circuit.** `AddDbContext` (Scoped) + a long-lived
  SignalR circuit means one `DbContext` instance is reused for the whole user session. `DbContext` is not
  thread-safe → overlapping operations (double-submit, concurrent component loads, background refresh) throw
  *"A second operation was started on this context…"*, plus stale reads from accumulated tracking. Web-only
  (desktop gets a fresh request scope per API call). Fix: `AddDbContextFactory` + context-per-operation.
- **H2 — `Title` length mismatch (300 vs 200).** Forms validate `StringLength(300)`; the column is
  `HasMaxLength(200)`. Silent on SQLite (no length enforcement) but a `DbUpdateException` on
  SQL Server/PostgreSQL/MySQL — the exact providers the project says are swappable.
- **H3 — Mass assignment on issue update.** The PUT binds and copies `Status`, `Resolution`, `AssigneeId`,
  `IsSticky`, and **`IsPrivate`** straight from the request body (`IssueEndpoints.cs:102`), with no
  field-level authorization, no status-transition validation, and no check that `AssigneeId` is a project
  member. An Updater can un-private an embargoed issue or jump status to hide a bug.
- **H4 — Note-add / issue-create require only authentication.** `POST /api/issues/{id}/notes` and
  `POST /api/projects/{projectId}/issues` check only that the caller is authenticated and the target exists —
  no membership/visibility check. (Same root as C2.)
- **H5 — Passwords and bearer tokens travel over cleartext HTTP.** `UseHttpsRedirection` is commented out
  ("LAN, plain HTTP"); desktop points at `http://localhost:5003`. Login passwords and long-lived bearer
  tokens are sniffable on the LAN path. *Partly a deployment decision — see open question.*
- **H6 — Web runs as static SSR, so the Issues project-filter dropdown is a dead control.** No shared page
  declares `@rendermode`; the CRUD forms work via the static-SSR form-post pattern, but
  `Issues/Index.razor`'s `<select @bind=…>` needs an interactive circuit that doesn't exist in the web host.
  Changing it does nothing on web (works on desktop's BlazorWebView — inconsistent across hosts).
- **H7 — `IssueHistory` is write-only.** Status/assignee changes faithfully record history rows, but there
  is no GET endpoint, no data-service method, and no UI that ever reads them. The audit trail is invisible.

### MEDIUM

- **M1 — Sticky-sort parity break.** Web orders `IsSticky` then `UpdatedAt`; the API endpoint orders only by
  `UpdatedAt`. The "Sticky (pinned to top)" checkbox works on web, silently does nothing on desktop.
- **M2 — No optimistic-concurrency token.** Read-modify-write with last-write-wins; concurrent triage
  silently loses updates. Add a `RowVersion` and surface `DbUpdateConcurrencyException`.
- **M3 — Dead second role system.** `.AddRoles<IdentityRole<int>>()` creates `AspNetRoles`/`AspNetUserRoles`
  that nothing ever reads or writes; all authz uses the custom `User.Role`. Anyone who later assigns a role
  via Identity's normal APIs sees zero effect — the two stores can diverge silently.
- **M4 — Half-wired model layer (built but no working surface).** `Issue.ExpectedBehavior`/`ActualBehavior`,
  `AffectsVersionId`/`FixVersionId` + the whole `ProjectVersion` entity, `DueDate`, `Reproducibility`
  display, and the whole `IssueAttachment` entity exist in the model + migration but appear in no DTO, form,
  or endpoint. A user can neither set nor see any of them.
- **M5 — Categories and members can be *selected* but never *created*.** Read endpoints feed the dropdowns,
  but there's no create-category and no add-member endpoint/UI. Categories are always empty; the Assignee
  dropdown can only ever contain the project creator (auto-added as the sole member).
- **M6 — `ProjectMembership.Role` is written but never read.** Creator is stored as project Manager; nothing
  consults it. (Same root as C2.)
- **M7 — `User.IsActive` is never checked.** Deactivated users can still sign in and act; no UI to toggle it.
- **M8 — Open registration + racy admin bootstrap.** `RequireConfirmedAccount=false` and public
  registration; the *first web registrant* becomes Administrator via a `Users.Count()==1` check
  (`Register.razor:94`) — "first HTTP caller wins," racy under concurrent registration, and web-only (an
  API-first install gets no admin). There is **no role-management UI**, so no one else can ever be promoted.

### LOW

- **L1** — Empty-note behavior differs: web silently no-ops, desktop throws (API returns 400).
- **L2** — Project-existence check exists only on the API path; the web path relies on a raw FK exception.
- **L3** — Create-issue-plus-history isn't atomic (two `SaveChanges`); a failure leaves an issue with no
  creation-history row.
- **L4** — No paging anywhere; result sets are unbounded.
- **L5** — Desktop bearer token is a role snapshot; role changes need re-login (web cookie re-validates).
- **L6** — Orphan template pages `Counter.razor` (`/counter`) and `Weather.razor` (`/weather`): routed, no
  nav, no `[Authorize]`. Remove.
- **L7** — Dead code: `Infrastructure/Class1.cs` (empty template class), `UI/Services/PolicyNames.cs`
  (constants never referenced — pages use string literals).
- **L8** — Desktop `.csproj` targets a single Windows-only TFM while comments/`maccatalyst` conditions claim
  macOS support; Mac Catalyst is not actually a build target.
- **L9** — Desktop API base URL is hardcoded in `appsettings.json` with a `TODO` for a settings screen that
  doesn't exist.
- **L10** — Template-leftover nav ("About → learn.microsoft.com") in both web and desktop layouts.

### Verified clean (checked, no defect)

XSS (no `MarkupString`/raw-HTML sinks; all user content auto-escaped) · SQL injection (all LINQ/parameterized;
no raw SQL) · CSRF (web uses antiforgery + `EditForm`; API is stateless bearer) · role check fails **closed**
on missing/unparseable claim · single Identity password store (no plaintext/duplicate credential field) · no
hardcoded JWT signing key or secrets in source/config · EF migration + model snapshot in sync (no drift) ·
enums round-trip as ints correctly · read queries use `AsNoTracking` + correct `Include`s (no N+1) · DTO
shapes and routes match field-for-field between web and desktop · entity cascade/restrict/set-null behavior
is sane (no unexpected orphaning).

## Fix order (proposed)

1. **Access control (C1, C2, H3, H4, M6)** — one shared, membership-and-visibility-aware authorization
   helper used by *both* the API and EF paths so they cannot drift. *(Depth is an open question — see below.)*
2. **Correctness that will break real use (H1 DbContext factory, H2 Title length, M1 sticky sort, M2
   RowVersion, L3 atomic writes).**
3. **Interaction/host bugs (H6 render mode).**
4. **Honesty about scope (M3 dead role system, M4/M5 half-wired layer, H7 history, L6–L10 cleanup)** — finish
   or explicitly mark-as-future + remove decorative dead UI. *(Open question.)*
5. **Build the real test suite** — regression test for every fix (playbook rule), starting with the
   access-control matrix and the deck/parity cases.

## Remediation status (branch `claude/audit-fixes-2026-08-10`)

**Fixed + tested (committed):**
- **C1, C2, H3, H4, M6** — per-project access control, enforced identically on the API and web/EF
  paths via a shared decision layer (`AccessContext` / `VisibilityQueries`). 30 tests.
- **H1** DbContext-per-operation; **H2** form/column length match; **L3** atomic issue+history;
  **M1** sticky-sort parity; **M3** dead role registration removed; **M7** IsActive enforced at
  sign-in; **M8** safe admin bootstrap. 4 more tests. Dead code / orphan pages removed (L6, L7).

**Also fixed + committed (Phases 3–4):**
- **Member management** — add/remove members, set per-project role (Manager-gated), on both the
  shared UI and API; `/projects/{id}/members` page. **User/role admin** — web-only `/admin/users`
  (set global role, activate/deactivate; no self-lockout).
- **M4** — Expected/Actual behavior, Reproducibility, DueDate, and Affects/Fix **Version** selectors
  wired end-to-end (forms + detail + both data paths + API); `ProjectVersion` is now fully reachable.
- **M5** — category creation + version CRUD via a Manager-only `/projects/{id}/settings` page.
- **H6** — Issues project-filter reworked as a portable form-GET (was a dead interactive `@bind` in
  the web host). **H7** — IssueHistory read view on the issue detail page.
- **Private notes** — `IssueNote.IsPrivate` now settable (Developer+) and shown, already filtered from
  unauthorized viewers by the Phase 2 rule. **L10** — template nav leftovers removed.

**Attachments — DONE** (branch `claude/issue-attachments`). The orphaned `IssueAttachment` entity is
now wired end-to-end on both hosts with the security controls the reviewer flagged:
- **Storage** (`IAttachmentStorage`/`FileSystemAttachmentStorage`): files stored OUTSIDE any web root
  under a configurable path, named by a server-generated 32-hex GUID key with no extension (client
  filename never touches the path → no traversal), the read path validates the key, and a configurable
  size limit is enforced (over-limit uploads abort and clean up). Original filename kept as display
  metadata only. Guarded by 8 storage-security tests.
- **Endpoints:** API (bearer) + web (cookie + antiforgery) list/upload/download/delete, each
  re-checking the Phase 2 ACL (view to list/download, `CanAddNote` to upload, uploader-or-Updater to
  delete). Downloads served `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff` so an
  uploaded HTML/SVG can't execute.
- **Cross-host UI:** the shared issue page branches on an injected `IAttachmentTransfer.Host` — web
  (static SSR) uses a plain multipart form + anchor links; desktop (BlazorWebView) uses `<InputFile>`
  streaming to the API and interactive download-and-open — because a shared page can't declare an
  interactive render mode.

**Deferred (own follow-up, by design):**
- **H5 HTTPS posture** — deployment decision (documented trusted-network plain-HTTP vs enforced TLS).
- **L8** desktop Mac-Catalyst TFM, **L9** desktop API-URL settings screen — minor, documented above.

## Discovered during remediation

- **D1 — Passkey migration/model drift (design-time). FIXED** (branch `claude/fix-passkey-migration-drift`).
  Root cause: a chat-created `AppDbContextFactory` built the design-time context with a bare
  `new AppDbContext(options)` — no application service provider, so ASP.NET Identity's SchemaVersion
  (v3) never applied and the .NET 10 `AspNetUserPasskeys` entity dropped out of the model. Every
  `dotnet ef` scaffold then tried to `DropTable("AspNetUserPasskeys")`, which would delete real
  credentials (passkeys are live here: login + Manage/Passkeys). Fixed by building the design-time
  context through the SAME registrations the app uses (`AddOpenTrackInfrastructure` +
  `AddOpenTrackIdentity` via the `IDbContextFactory`) — a minimal `AddIdentityCore(SchemaVersion=v3)`
  is not enough. A probe scaffold now yields an EMPTY migration. Runtime was confirmed never affected
  (the H1 factory change did not break passkeys). Guarded by `RuntimeModelTests` +
  `DesignTimeFactoryTests`.
- **D2/M2 — `RowVersion` optimistic concurrency. FIXED** (unblocked by the D1 fix). A `Guid RowVersion`
  concurrency token on `Issue`/`Project` (migration `AddConcurrencyTokens`), round-tripped through the
  edit forms; a stale write raises `DbUpdateConcurrencyException`, surfaced as
  `ConcurrencyConflictException` (web) / HTTP 409 (API) telling the user to reload — instead of
  silently overwriting a concurrent edit. Proven by `ConcurrencyTests`.

## Open questions requiring a product decision

- **Access-control depth:** full Mantis-style per-project membership ACL (requires building member
  management, which is currently M5) vs. enforce-what-exists-now (private issues → reporter/assignee/Dev+;
  private projects → members) vs. lock-down-simple (auth + global role only, and remove the `IsPrivate`/
  `IsPublic` toggles until the real model exists so they don't imply false privacy).
- **Half-wired feature layer (M4/M5/H7):** finish-wire now, or defer-as-future + remove the decorative bits
  that imply they work today.
- **Cleartext HTTP (H5):** enforce HTTPS even on-LAN, or keep plain HTTP as a documented trusted-network
  deployment choice.
